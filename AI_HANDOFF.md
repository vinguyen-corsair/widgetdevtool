## D4 - Widget Personalization (`personalization.py`, `personalization_panel.py`, `settings_panel.py`, `runtime_bridge.py`, `main_window.py`)
Source traced (iCUE v5.55): `widgetshelpers/src/WidgetPersonalizationSettings.cpp`, `dashlcdui/models/WidgetBuilderPersonalizationSettings.cpp`,
`models/ActivePersonalizationSettingsModel.cpp`, `widgetcontent/PersonalizationSettings.h/.cpp`, `DeviceSettings`, `ScreenSettings`,
`panels/WidgetBuilderPanelSettingsModel.cpp`, `htmlwidgetcore/.../EditorSettingsModels.cpp`, `HtmlSettingsImpl.cpp`, `WidgetBuilderPersonalizationPanel.qml`.
- **Raw vs effective.** The instance (`WidgetInstance.data`) is the raw map and is never rewritten by personalization. `RuntimeBridge` builds what the page receives from
  `effective_settings(raw, active)` (`bridge.effective_data()`; `bridge.data` = effective + url + typeId). `set_properties()` still writes the instance only.
- **The rule** (`settings()`): Present (default TRUE when missing) false -> raw; CustomStyleEnabled (default false, `toBool`) true -> raw; otherwise ONLY keys the instance
  already has are replaced: textColor, accentColor, accentColor2 <- active text/accent/accent2; backgroundColor <- widgetBackgroundColor; transparency <- widgetTransparency
  (int); backgroundMedia <- the stored map with `pathToAsset = ""` (other fields kept, a non-map becomes `{pathToAsset: ""}`). Nothing is added.
- **Defaults** (`PersonalizationSettings.h`): text `#ffffff`, accent and accent2 `#f08e33`, widget background `#000000`, widget transparency `80` (int).
- **Device vs screen** (verified): `ActivePersonalizationSettingsModel`: active = the Screen settings when `DeviceSettings.themeByScreenEnabled` (default false) else the Device
  settings. `PersonalizationModel` keeps Device values, Screen values and the flag PER DEVICE profile (`free` when no device is selected). Our choice: one Screen per device.
  Window state only: not saved in the instance or the instance file.
- **Markers.** Opening iCUE's settings panel sets Present := "the map has any of the six keys". The bridge does this when it is created (`sync_present`), as a non-edit
  (`set_value(..., mark_edited=False)`), and only for a widget that has such keys. DIFFERENCE: iCUE also writes `Present=false` for a widget without the keys; we write nothing
  so no property the widget did not declare appears (the effective map is identical). Both markers are visible to the widget (`window.widgetPersonalizationCustomStyle*`)
  because they are in the map in iCUE too. `refresh_from_source` (live reload) keeps both markers; `merge()` carries only Enabled (iCUE `update()`).
- **UI.** `SettingsPanel`: the LAST group is the Widget Personalization panel (single group: that group is both), with the `Custom Style` switch and iCUE's text
  "Widget Personalization is disabled, Screens Personalization settings will be applied to the widget layout." While Custom Style is off the six personalization editors are
  hidden (only when Present is true, as in `EditorSettingsModels.cpp`; other editors of that group stay). The editors show the STORED value; a note says what the widget
  receives when that differs ("Runtime receives X (stored: Y)"). `PersonalizationPanel` (below the settings) edits the Device/Screen values and theme-by-screen.
- **Lifecycle.** Custom Style switch, a personalization edit, theme-by-screen or a device change -> `bridge.refresh_effective()` -> `dataChanged` -> `window[key]` + `onDataUpdated`;
  no page reload. A personalization change that leaves the effective map equal sends nothing (our choice; whether iCUE calls `onDataUpdated` then is Unknown).
- **backgroundMedia.** Off: the page gets `pathToAsset=""`. On: the stored map passes through. The media-selector editor is unsupported, the personalization's own background image
  (imageSource, scaling, position, rotation, blur) is NOT simulated, and `toQmlString` turns a map into `""` for the page (existing quirk), so the page cannot show a difference.
- **Raw settings and device changes.** Device/size/orientation changes only change which personalization is active; the instance is untouched (tested: no reload, same data).

## D6 - device viewport (`viewport.py`, device bar in `main_window.py`)
- Device / Size / Orientation / Mode / Preview scale in the top bar (`MainWindow.select_device(...)` is the API). Window state only: it is not part of any instance,
  a change does not reload the page (the page gets a normal `resize` event), does not touch instance data, and live reload and the settings editor keep working.
- NOMINAL (default) = `widgetsize_utils::size()`: relative size x **mimicScreenSize** (portrait: width x mimic.height, height x mimic.width), truncated with `int()` like
  `screenSizeText()`. Keyboard / pump: the fixed manifest size. PHYSICAL (EXPERIMENTAL, dashboards only) = relative size x **physicalScreenSize**, the layout of
  `DashLCDScreenView.qml` at zoom 1. `physicalScreenSize` is also what iCUE uses to find the OS monitor of the device (`findScreenWithSimilarSize`).
- The page keeps its CSS size: `window.innerWidth/innerHeight` = viewport (measured in tests for every size x orientation x device, nominal and physical).
  Smaller preview = page zoom factor: view = W*z pixels, so the page still lays out in W px. Only zooms k/g (g = gcd(W,H)) keep the measurement exact, so the combo offers
  Fit + those; Fit uses one of them when within 25 %, else an approximate zoom. The label next to the bar shows what the page measures and flags any mismatch.
  Known side effect: `window.devicePixelRatio` is multiplied by the zoom (tested).
- Free size (default) = the old behaviour: the page fills the preview area.

## D3 - what exists
- `settings_editors.py`: one `SettingEditor` per `SettingParameter`, generated only from the parsed metadata (nothing names a widget or property).
  `EDITABLE_TYPES` = switch, slider, combobox, tab-buttons, slider-enum, textfield, color, time-format.
  Commit rules: switch/slider/combobox/tab-buttons/slider-enum/color/time-format commit on the user action; textfield commits on Enter or focus-out, Esc reverts.
  Nothing is clamped; a stored value outside [min,max] or outside the options is shown + flagged and kept. A missing key is shown empty ("Key not stored")
  and is created only by the first edit. Personalization keys: see D4 (hidden while Custom Style is off, runtime note).
- NOT supported (shown as "Unsupported: <reason>", read-only, never commit): `media-selector`, `colors`, `sensors-combobox`, `sensors-factory`,
  `search-combobox`, `accounts-list`, `app-status`, `stream-deck-virtual-device`; a combobox/tab-buttons/slider-enum whose options failed to evaluate;
  controls without a parameter (`media-session`, unknown data-type) are listed as "Not editable".
- Flow: control -> `settingCommitted` -> `MainWindow._on_setting_committed` -> `WidgetInstance.set_value` -> `RuntimeBridge.set_properties` ->
  `window.<key>` + `onDataUpdated`. No page reload; an equal value does nothing.
- Instances in the UI: new instance (own id), switch between instances of the store, save/open JSON, open as restore or merge. Live reload keeps the instance
  and its edited values.

## D3 test strategy (no blanket ignores)
- Generic real-widget test (`RealWidgetTests.exercise`): console errors present right after load are the baseline (classified `network` vs `runtime` by
  `classify_console_error`; a `runtime` error at load fails the test). Any error appearing after the edits fails the test, whatever its class.
- Textfields whose value or name marks a structured value (`is_format_bound`: URL, path, JSON, e-mail; names containing url/uri/path/file/font/mail/link/
  address/host) are not mutated by the generic test (reported as skipped). They are covered by `UrlFieldFlowTests` with a valid URL on a local fixture:
  Settings -> Instance -> Runtime -> `onDataUpdated` (once) -> no reload -> no console error -> survives live reload.
- The name heuristic is a test helper, not product logic. Plain textfields (`label` fixture) are covered by `RuntimeFlowTests`.
- The generic test does not check that a real widget then behaves well with the new value (e.g. feed actually loads): that needs a valid endpoint = Unknown.

## Window growth bug (found after A2; layout fix in `main_window.py`, `personalization_panel.py`)
**Root cause (measured on the real `windows` platform, not a test-harness effect):** the layout set the WINDOW's minimum size. A plain `QLabel` / `QComboBox` / `QCheckBox` reports its whole text (or widest item) as MINIMUM width, and `QMainWindow` applies the layout minimum to the window, so (1) the window opened at 1667x831 instead of the coded 1100x760 (device combo 434 px, mode/scale combos, `device_info`, `watch_label`...), and (2) every Device/Size/Orientation change that produced a longer text (`device_info`, the measurement label with A2's "display scaling ...", the Personalization group title with the device name) raised the minimum and the window grew (1667 -> 1763 -> 1872 px wide) and never shrank back. No test resized the window except the harness' own initial `resize(1500, 900)` and `setFixedSize(300, 200)` on the PREVIEW frame (it is not the cause); finished test windows were only `shutdown()`, never closed, so under a visible platform they piled up on screen.
**Fix:** `ClippedLabel` (minimum width 1, tooltip = full text) for `path_label`, `watch_label`, `device_info`, `measured_label`; `narrow_combo` (minimum contents length) for the five device combos; `status` has a fixed 3-line height; Personalization panel: constant group title (the device name moved into `active_label`, now word-wrapped), the check box has an explicit minimum width; the main layout uses `SetNoConstraint` (the layout can no longer resize the window) with an explicit minimum size taken once from the first layout (>= 900x600, bounded by the screen); the side column (instances, settings, personalization) is inside a `QScrollArea` (`side_scroll`, min 450 px) and the splitter children cannot collapse; opening the Widget Library docks it at 360 px and grows the window ONCE only if the central area would fall below its minimum (never shrinks, never beyond the screen, toggling does not grow again); `shutdown()` now hides the window. **Measured after (windows platform, RSS Feeder, S -> XL -> S, portrait/landscape, Native and Fit):** window 1100x820 and preview frame 617x266 in EVERY step (before: 1667x831 growing to 1872x831); only the viewport inside the frame changes; a viewport larger than the frame scrolls (canvas up to 605x967). **Tests** (`WindowSizeStabilityTests`, run on both `offscreen` and `windows`): cycling every device/size/orientation twice in Native and Fit keeps window size, frame size and minimum size identical; S/XL/S x6; a large viewport scrolls and the window stays; the panels (side column, console, frame, status) stay inside the window and do not move; the Widget Library opens inside the window, makes room once and toggling does not grow it; `shutdown()` hides the window.
